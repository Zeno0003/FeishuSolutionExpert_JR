# 飞书开发入门全景指南

> **速览** 把飞书开发按"做什么 → 写多少代码 → 用什么工具"分为四个层次，而非官方文档的 API 域分类。程序员上手路径：创建应用 → API Explorer 试调 → SDK 写 Bitable 读写 → 事件订阅。

## 零、核心框架：为什么官方文档看着乱？

飞书开放平台官方文档（open.feishu.cn）按 **API 业务域** 组织：IM 消息是一个域、通讯录是一个域、日历是一个域……每个域有自己的 REST 端点、请求体和响应体。

这没问题——如果你已经知道你需要哪个 API。但作为刚接触飞书开发的程序员，你的问题是另一个顺序的：

> "我想把数据库里的数据自动写到多维表格" → 我该用什么？Webhook？API？SDK？aPaaS？集成平台？

官方文档不按这个顺序组织。下面是一个**四层心智模型**，帮你从"我想做什么"出发，逐层定位到"用哪个工具怎么做"。

### 第〇层：你想"开发出"一个什么东西？（应用形态）

在飞书上开发，最终产物是以下 **5 种形态之一**：

| 形态               | 是什么                   | 谁用          | 典型场景             |
| ---------------- | --------------------- | ----------- | ---------------- |
| **企业自建应用**       | 你自己公司内部用的 App，只有本公司能用 | 本公司成员       | 内部自动化、数据打通、定制功能  |
| **应用商店应用 (ISV)** | 发布到飞书应用目录，其他公司安装      | 多公司租户       | SaaS 产品、跨企业工具    |
| **Bitable 插件**   | 嵌入在多维表格里的功能扩展块        | 使用该 Base 的人 | 表格自定义视图、增强数据处理   |
| **机器人 (Bot)**    | 在聊天窗口里交互的应用           | 群聊/单聊用户     | 通知推送、对话式查询、快捷操作  |
| **网页应用 (H5)**    | 嵌在飞书客户端内的网页           | 飞书用户        | 复杂业务 UI、仪表盘、管理后台 |

> 对大多数程序员来说，入手就创一个**企业自建应用**，把需要的"能力"（Bot / Web 应用 / 插件）勾上就行。

### 第一层：你打算写多少代码？（开发层级）

这是解决"有多少种方式"这个问题的核心分层：

**0% 代码 — 零代码**

| 方式                  | 说明                          | 能做什么                                                           |
| ------------------- | --------------------------- | -------------------------------------------------------------- |
| **多维表格自动化**         | Base 内建的自动化流程引擎，触发条件 → 执行动作 | "当字段 X 变化时自动修改字段 Y"                                            |
| **自动化 Webhook 触发**  | 外部系统 POST 一个 URL，触发自动化流程    | "外部系统发一个 HTTP 请求 → Base 新增记录" ← 详见 [[Base 自动化 Webhook 触发实操流程]] |
| **集成平台 (AnyCross)** | 飞书内置的连接器平台，拖拽配置             | 飞书 ↔ CRM/ERP/数据库 的数据同步                                         |
| **飞书妙搭 (Miaoda)**   | AI 对话式搭应用，描述需求即生成           | 零基础快速搭出 CRUD 应用                                                |

**30% 代码 — 低代码**

| 方式              | 说明                            | 能做什么             |
| --------------- | ----------------------------- | ---------------- |
| **飞书 aPaaS**    | 强低代码平台，有可视化数据建模 + 页面设计 + 流程引擎 | 带 UI 的业务系统，复杂审批流 |
| **审批流引擎**       | 拖拽设计审批流程，节点可写脚本               | 请假、报销、合同审批等      |
| **Bot Builder** | 低代码搭建机器人，拖拽配置对话流程             | 客服机器人、查询机器人      |

**100% 代码 — 全代码（这是你的主场）**

| 方式                            | 说明                                        | 能做什么                                      |
| ----------------------------- | ----------------------------------------- | ----------------------------------------- |
| **REST API + SDK**            | Python / Go / Java / Node.js 直接调飞书服务端 API | 完全自由，读写飞书任何数据                             |
| **事件订阅 (Event Subscription)** | 飞书把发生的事（消息、审批、通讯录变更）推送到你的服务器              | 实时响应飞书内的事件                                |
| **HTTP Webhook 模式**           | 你需要一个公网 URL，飞书 POST 事件到你的服务器              | 传统 Server 部署                              |
| **WebSocket 长连接模式**           | 你的程序主动连飞书，维持一条长连接收事件                      | 不需要公网 URL，适合内网开发 ← 详见 [[飞书 Webhook 全景解析]] |

**AI 驱动**

| 方式                 | 说明                          | 能做什么                |
| ------------------ | --------------------------- | ------------------- |
| **飞书 Aily**        | AI Agent 平台，配置知识库 + 工具 + 插件 | 智能问答、自动分类、Agent 编排  |
| **Aily API / SDK** | 程序化控制 Agent、管理知识空间          | 把 AI Agent 嵌入你自己的系统 |

### 第二层：你能操作什么数据？（API 能力域）

当你选择"全代码"路线后，飞书提供 **2500+ Open API**，按域分类。以下是程序员最常用的域：

| 域                      | API 前缀        | 核心操作                    |
| ---------------------- | ------------- | ----------------------- |
| **多维表格 (Bitable)**     | `bitable/v1`  | 表/字段/视图/记录的增删改查 ← 你最关心的 |
| **云文档 (Drive)**        | `drive/v1`    | 文件上传下载、权限管理             |
| **云文档内容 (Docx/Sheet)** | `docx/v1`     | 文档和电子表格的内容读写            |
| **IM 消息**              | `im/v1`       | 发文本/卡片/图片/文件消息，群管理      |
| **通讯录**                | `contact/v3`  | 部门、用户、用户组 CRUD          |
| **日历**                 | `calendar/v4` | 日程增删改查、会议室、忙闲查询         |
| **审批**                 | `approval/v4` | 审批定义、实例创建、任务处理          |
| **任务**                 | `task/v2`     | 任务列表、任务、子任务 CRUD        |
| **人事**                 | `corehr/v1`   | 员工、部门、岗位数据              |

> 每个域在官方文档中都是独立的一章。知道你要操作什么数据 → 定位到对应的 API 域 → 看那个域下的端点列表。

### 第三层：数据怎么流入流出？（连接机制全景）

你用全代码方式操作飞书数据，有 **5 条路径**：

| #   | 路径                   | 方向         | 代码量             | 适用场景                            |
| --- | -------------------- | ---------- | --------------- | ------------------------------- |
| ①   | **自动化 Webhook 触发**   | 你的系统 → 飞书  | 0（只需 HTTP POST） | 最简单的通知写入：外部事件来了一条，自动往 Base 加条记录 |
| ②   | **Bitable REST API** | 你的代码 → 飞书  | 100%（写代码）       | 复杂 CRUD：批量新增、条件更新、删除记录          |
| ③   | **自动化 HTTP 请求**      | 飞书 → 你的系统  | 0               | Base 数据变化时，飞书自动调你的 API          |
| ④   | **群机器人 Webhook**     | 你的系统 → 飞书群 | 0-10%           | 把报警/通知/报表推送到某个群里                |
| ⑤   | **SDK 完整集成**         | 双向         | 100%（写代码）       | 构建完整应用，读写任意飞书数据，处理事件回调          |

> 路径 ④ 和 ① 的区别：④ 是推到群聊（人可以看），① 是触发 Base 自动化（机器处理数据）。路径 ⑤ 是 ② 加上事件订阅，实现双向交互。

## 一、Bitable 数据写入专题

你问"怎么样可以开发某些东西直接写入数据到飞书多维表格中"——这是最实操的问题。以下是 **5 条写入路径** 的完整对比：

### 路径 ①：Webhook 触发自动化（推荐最简单场景）

**适合**：外部系统通知来了，自动在 Base 里新增/修改一条记录。

**怎么做**：
1. 在 Base 中创建一个自动化流程，触发器选「Webhook 触发」
2. 飞书给你一个 URL（含 token）
3. 你的外部系统 POST JSON 到这个 URL
4. 自动化收到 JSON 后，执行「新增记录」动作，把 JSON 字段映射到表格字段

**代码量**：零——你的系统只需发一个 HTTP POST。
**限制**：50 次/秒/Base，每次请求只能触发一个自动化流程。

> 详细步骤见 [[Base 自动化 Webhook 触发实操流程]]

### 路径 ②：Bitable REST API 直接写入

**适合**：需要精细控制——批量新增、条件更新、查重后决定新增还是更新等。

**怎么做（以 Python 为例）**：

```python
# pip install lark-oapi
import lark_oapi as lark

# 1. 创建 client（自动管理 token）
client = lark.Client.builder() \
    .app_id("cli_xxxx") \
    .app_secret("xxxx") \
    .build()

# 2. 新增一条记录
request = lark.bitable.v1.CreateAppTableRecordRequest.builder() \
    .app_token("B8qJbG1GDarbEksW4DacVfTIn0d") \
    .table_id("tblxxxx") \
    .request_body(lark.bitable.v1.AppTableRecord.builder()
        .fields({
            "姓名": "张三",
            "状态": "进行中",
            "金额": 1000
        })
        .build()) \
    .build()

response = client.bitable.v1.app_table_record.create(request)
```

**关键参数**：
- `app_token`：你的 Base ID，从 Base URL 中获取（`https://xxx.feishu.cn/base/B8qJbG1GDarbEksW4DacVfTIn0d` 中的那串）
- `table_id`：表 ID，从 Base URL 中获取（`?table=tblxxxx` 或从 API 列出来）
- `fields`：字段名（用飞书界面上的显示名即可）→ 值的映射

**代码量**：安装 SDK + 5 行核心代码。
**限制**：需要先创建企业自建应用并申请 `bitable:app` 权限。

> Bitable API 官方文档：https://open.feishu.cn/document/server-docs/docs/bitable-v1/bitable-overview

### 路径 ③：自动化 HTTP 请求（飞书主动推数据出去）

**适合**：Base 数据变了，飞书主动通知你的系统。

**怎么做**：
1. 在 Base 自动化中，触发器用「记录创建/修改」
2. 动作选「HTTP 请求」
3. 飞书把记录数据 POST 到你的 API 端点

**方向是反的**：飞书 → 你。通常与路径 ② 配合使用（你推入数据 → Base 处理 → 飞书通知你结果）。

### 路径 ④：群机器人 Webhook（推到群里给人看）

**适合**：把数据推送到群聊场景（报警、日报、审批提醒），而非写入 Base。

```python
import requests
url = "https://open.feishu.cn/open-apis/bot/v2/hook/xxxx"
data = {"msg_type": "text", "content": {"text": "今日新增客户：5 位"}}
requests.post(url, json=data)
```

> 详见 [[群机器人 Webhook 实操流程]]

### 路径 ⑤：SDK 全能力读写（最灵活）

与路径 ② 本质相同，区别是加上事件订阅后可以实现：
- 用户在 Base 里做了操作 → 飞书推送事件给你 → 你的代码处理 → 调用 API 写回 Base

这是最完整的方案，适合需要**复杂业务逻辑**的场景。

### 路径选择速查表

| 你的场景                | 推荐路径               |
| ------------------- | ------------------ |
| 外部系统有事件了，往 Base 记一笔 | ① Webhook 触发自动化    |
| 我需要自己程序读写 Base 数据   | ② Bitable REST API |
| Base 数据变了通知我的系统     | ③ HTTP 请求动作        |
| 把消息发到群里             | ④ 群机器人 Webhook     |
| 完整应用，交互式体验          | ⑤ SDK + 事件订阅       |

## 二、跨 Base 操作专题

你问"如何根据一个 Base 的数据对另一个 Base 进行操作"——这里单独讲透。

### 方案 A：零代码（自动化链）

```
Base A 的自动化（记录创建/修改）→ HTTP 请求动作 → 你的中转服务器 → Webhook 触发 Base B 的自动化
```

或者更简单——如果你用集成平台 (AnyCross)：

```
集成平台连接器 → 读 Base A → 写 Base B（可视化配置）
```

**优点**：不用写代码。**缺点**：逻辑能力有限。

### 方案 B：低代码（aPaaS）

在飞书 aPaaS 中创建一个应用，绑定两个 Base 的数据源，在云函数中写业务逻辑：

```
aPaaS 云函数:
  1. 调 bitable API 读 Base A 的数据
  2. 业务处理（筛选、计算、去重等）
  3. 调 bitable API 写到 Base B
```

### 方案 C：全代码（你的程序做中介）

这是最灵活的方式。流程：

```
你的 Python/Go 程序:
  1. client.bitable.v1.app_table_record.list(app_token_A, table_id_A)
  2. 在代码中处理数据（过滤、转换、合并、计算）
  3. client.bitable.v1.app_table_record.create(app_token_B, table_id_B, processed_data)
```

或者用**定时任务**：每隔 5 分钟执行一次同步逻辑。

或者用**事件驱动**：订阅 Base A 的事件（记录变更），实时触发同步到 Base B。

**代码框架**：

```python
# 跨 Base 数据同步的核心逻辑骨架
import lark_oapi as lark

client = lark.Client.builder() \
    .app_id("cli_xxxx").app_secret("xxxx").build()

# 读取源 Base 数据
src_records = client.bitable.v1.app_table_record.list(
    lark.bitable.v1.ListAppTableRecordRequest.builder()
        .app_token("源Base的app_token")
        .table_id("tbl_src")
        .build()
)

# 写入目标 Base
for record in src_records.data.items:
    client.bitable.v1.app_table_record.create(
        lark.bitable.v1.CreateAppTableRecordRequest.builder()
            .app_token("目标Base的app_token")
            .table_id("tbl_dst")
            .request_body(lark.bitable.v1.AppTableRecord.builder()
                .fields(transform(record.fields))  # transform 是你的转换逻辑
                .build())
            .build()
    )
```

### 方案 D：AI 中介（Aily Agent）

让 Aily Agent 挂两个 Base 的知识空间，Agent 自动理解两个 Base 的结构并执行跨 Base 查询/操作。

### Bitable API 能做什么操作？

聚焦到你问的"有哪些操作"。Bitable API (`/bitable/v1/`) 覆盖以下全量操作：

| 操作 | API 端点 | 说明 |
|------|----------|------|
| 列出 Base 下所有表 | `GET /apps/{app_token}/tables` | 获取 Base 里的表清单 |
| 创建表 | `POST /apps/{app_token}/tables` | 在 Base 中新建一张表 |
| 删除表 | `DELETE /apps/{app_token}/tables/{table_id}` | 删除一张表 |
| 列出字段 | `GET /apps/{app_token}/tables/{table_id}/fields` | 获取表的所有字段定义 |
| 列出视图 | `GET /apps/{app_token}/tables/{table_id}/views` | 获取表的所有视图 |
| **列出记录** | `GET /apps/{app_token}/tables/{table_id}/records` | 读取表数据，支持筛选和排序 |
| **新增记录** | `POST /apps/{app_token}/tables/{table_id}/records` | 插入单条或批量记录 |
| **更新记录** | `PUT /apps/{app_token}/tables/{table_id}/records/{record_id}` | 修改指定记录 |
| **删除记录** | `DELETE /apps/{app_token}/tables/{table_id}/records/{record_id}` | 删除指定记录 |
| 批量新增 | `POST /apps/{app_token}/tables/{table_id}/records/batch_create` | 一次最多 500 条 |
| 批量更新 | `POST /apps/{app_token}/tables/{table_id}/records/batch_update` | 一次最多 500 条 |
| 批量删除 | `POST /apps/{app_token}/tables/{table_id}/records/batch_delete` | 一次最多 500 条 |
| 搜索记录 | `POST /apps/{app_token}/tables/{table_id}/records/search` | 按条件搜索（含筛选、排序、分页） |

## 三、CLI vs SDK vs API：关系辨析

这三个概念在官方文档中混在一起，这里彻底分清楚：

```
飞书开放平台开发工具层级

┌──────────────────────────────────────────────┐
│              飞书开发者 CLI                     │
│  (辅助工具，帮你创建/管理/调试应用)                  │
│  命令: feishu app create / feishu api call / .. .│
│  不是用来写业务逻辑的！                            │
└──────────────────────────────────────────────┘
                      ↓ 你用它创建好应用后
┌──────────────────────────────────────────────┐
│              SDK (语言封装层)                    │
│  Python: lark-oapi / Go: lark-oapi             │
│  Node.js: @larksuiteoapi/node-sdk             │
│  Java: lark-oapi                              │
│  ┌────────────────────────────────────────┐   │
│  │  SDK 帮你做了：                          │   │
│  │  - 自动获取和刷新 token                   │   │
│  │  - 自动处理分页（帮你拿完所有数据）          │   │
│  │  - 事件加解密（AES）                      │   │
│  │  - 类型安全（请求/响应的字段有 IDE 提示）    │   │
│  │  - 文件上传/下载                          │   │
│  └────────────────────────────────────────┘   │
│  模式: client.bitable.v1.app_table_record.list()│
└──────────────────────────────────────────────┘
                      ↓ SDK 底层发的是
┌──────────────────────────────────────────────┐
│              REST API (HTTP 层)                │
│  POST https://open.feishu.cn/open-apis/       │
│       bitable/v1/apps/{token}/tables/{id}/    │
│       records                                 │
│  Headers: Authorization: Bearer {token}       │
│  Body: JSON                                   │
│                                               │
│  你当然可以直接用 curl/requests 调，            │
│  但 token 管理、分页、加密都得自己写。            │
└──────────────────────────────────────────────┘
```

**一句话总结**：
- **API** 是底层 HTTP 接口，你用 `curl` 也能调
- **SDK** 是语言封装，帮你省掉 token / 分页 / 加解密这些 boilerplate
- **CLI** 是开发辅助工具，帮你创建应用、管理权限、调试 API——不是用来写业务代码的

> 官方 CLI 文档：https://open.larksuite.com/document/tools-and-resources/development-tools/overview-of-ide

## 四、程序员推荐上手路径

作为程序员，你已经知道怎么写代码，缺的是飞书这边的"菜单"。按下面 5 步走，一个小时能完成第一个飞书 API 调用：

### 第 1 步：创建应用（5 分钟）

1. 打开 [飞书开发者后台](https://open.feishu.cn/app)
2. 创建「企业自建应用」，起个名字（比如"我的数据同步工具"）
3. 拿到 **App ID** 和 **App Secret**，保管好

### 第 2 步：零代码调一次 API Explorer（5 分钟）

1. 在开发者后台左侧找到「API 调试」(API Explorer)
2. 选 `bitable` → `列出记录`
3. 填上你的 Base 的 app_token 和 table_id（从 Base 的浏览器 URL 中取）
4. 点发送，看 JSON 返回——你不需要写一句代码就知道 API 的请求/响应格式了

### 第 3 步：SDK 写第一个读写脚本（15 分钟）

```bash
pip install lark-oapi
```

```python
import lark_oapi as lark

client = lark.Client.builder() \
    .app_id("换成你的App ID") \
    .app_secret("换成你的App Secret") \
    .build()

# 读：拉取前 10 条记录
resp = client.bitable.v1.app_table_record.list(
    lark.bitable.v1.ListAppTableRecordRequest.builder()
        .app_token("换成你的Base的app_token")
        .table_id("换成表ID")
        .page_size(10)
        .build()
)

if resp.success():
    for item in resp.data.items:
        print(item.fields)
else:
    print(f"错误: {resp.code} {resp.msg}")
```

### 第 4 步：把上面的脚本改成写入数据

把 `list` 换成 `create`，构造 `fields` 字典传进去。如果表里有「姓名」和「状态」字段，字段名就用界面上的中文名。搞定。

### 第 5 步：考虑事件订阅（需要的时候才做）

当你需要"Base 里的数据变了 → 自动触发你的代码"，而不是你自己定时去问"有没有新数据"的时候，再加上事件订阅。

> 这一步比较复杂，涉及公网 URL（HTTP 模式）或 WebSocket 长连接配置。先不急——80% 的自动化场景不需要事件订阅。
